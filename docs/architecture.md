# Desktop architecture

This document describes the libraries, monitoring composition and developing student interface in the [desktop plan](DESKTOP_APP_PLAN.md). Milestone acceptance and measured verification belong in [development progress](PROGRESS.md); this document does not independently pass a milestone. The owner-first Windows host and monitoring runtime are implemented. The M5 working tree adds the student window; its UI and display-scaling gates remain open. Production native delivery (M6) and release retention/qualification remain later work.

## Implemented module responsibilities

- `SnuWatcher.Core`: immutable section identities, seat/quota models, opening and recipient policies, and inclusive local-date expiry. It has no network, persistence or Windows dependencies. [ADR 0003](decisions/0003-external-contribution-review.md) records the reviewed contribution and corrections.
- `SnuWatcher.Application`: source and persistence ports, pure observation/delivery/health projections, legacy confirmation, watch management, query planning, the monotonic monitor, batch recovery/pump, and `MonitoringRuntimeSession`. It owns logical work and its ordering without depending on SQLite, HTTP or Windows.
- `SnuWatcher.Infrastructure`: bounded anonymous SNU transport/parsers, the shared physical-request dispatcher, stored source policy and metadata gateway, plus the SQLite factory/command lane, transactional watch store and explicit read-only legacy reader. HTML/JSON and selected legacy files are untrusted input. It does not collect SNU credentials or submit registrations.
- `SnuWatcher.Windows`: validated activation, session-local UI forwarding, the separate current-user-only global database-owner gate, fixed runtime profiles and `WindowsMonitoringHost`. The host owns concrete store/source/gateway resources and composes the Application session; its alert channel is injected.
- `SnuWatcher.Desktop`: WPF course-search, watchlist and settings views, localized resources, tray lifecycle and fixed browser/clipboard action adapters. Early guarded private routes validate the runtime and student interface without native initialization or the normal profile. The original feasibility window remains available for native validation. The monitoring pump is not yet connected to native notifications in the normal student host.
- Four xUnit projects validate Core policies, Application behavior, source/real SQLite integration and Windows ownership/hosting. Direct native display and browser clicks require the interactive acceptance protocol; a fake channel cannot establish those outcomes.

The solution and shared build properties pin .NET, enable nullable analysis, and preserve locked dependency graphs. CI has read-only repository permissions and runs offline relative to SNU. It does not send notifications or publish a public release.

## Student-interface ownership

Windows presentation controllers publish immutable snapshots through an explicit UI dispatcher. Search editing does not request data; catalog loading and search are explicit owned commands. A section can enter a watch only through its catalog-confirmed full identity and the current verified search results. Saved counts, current availability, loading status and failed source evidence remain separate. The offline term-label cache cannot establish a valid source selector.

`StudentDesktopSession` owns search, watchlist, settings and shell controllers, a local age timer, and a bounded operating-system state bridge. It consumes runtime hints and marshals UI updates; age ticks do not query SQLite or SNU. The shell coalesces committed-change hints into watchlist reloads and preserves failed reloads for retry. Preference updates use revision-checked storage and preserve unrelated draft edits.

The app owns both the desktop session and `WindowsMonitoringHost`. It supervises failures from each, closes admission, starts their drains concurrently, and retains ownership when finalization is blocked. The graph never disposes the host. Actual host workers and observers are joined before process shutdown; an asynchronous wrapper completing is not permission to release a still-running owner.

Views own visual resources and input routing. They use system colors, English/Korean resource dictionaries, independently bounded result/detail panes and compact navigation for small work areas. External actions resolve a closed destination enum to fixed official registration or SNU Genie pages; source strings cannot become executable markup, arbitrary browser URLs or shell commands. Alerts history remains an explicit placeholder until M6.

## Domain state and persistence

M3 established durable subscription/member state, atomic observation/event/outbox writes, replay-safe receipts, legacy import and lifecycle/send ordering. M4 extends that store through separate source-policy, batch-delivery, recovery and paged-work capabilities; all capabilities in one runtime must represent the same logical database. The external Application patch's storage and scheduling contracts are not adopted. The Python reducer/tests remain a behavioral reference, not the desktop host's production engine. PDF import is excluded.

The store verifies the pinned native SQLite identity before opening a file, recognizes its schema before journal changes, and rechecks a fresh schema under the write reservation to avoid concurrent initialization races. Schema upgrades preserve a verified pre-upgrade backup. Operations execute on a bounded background lane with private-cache connections, foreign keys and explicit durability. Completion health, valid baseline, member initialization, event, recipients, outbox and receipt share one transaction. Identical replay returns its original event ID before version checks; conflicting replay fails. [ADR 0002](decisions/0002-domain-persistence.md) and the [dependency record](sqlite-dependencies.md) describe the contract and runtime evidence.

The latest completed attempt and the last successful counts are separate facts. A failed, incomplete or changed response does not turn an old baseline into fresh availability. Prepared effects carry section/catalog versions for atomic comparison; current evaluation/commit time controls recipient expiry. Pure section/group health projections expose the last success, historical counts, current coverage, delay/unavailability and clock anomalies without inventing a new observation time or personal registration eligibility.

[Legacy migration](migration.md) documents explicit source selection, bounded read-only snapshots, catalog confirmation, historical provenance, the atomic idempotent import ledger and backup/recovery boundaries. Imported counts never initialize a live baseline or acknowledge an alert.

## Source admission and freshness

`ICourseSource` returns immutable complete, partial or failed reads. Catalog selectors remain opaque and exact. Section keys retain all six identity fields, including leading-zero sections; there is no current-term or alias fallback. Verified rows from a partial search remain usable, while absent or invalid rows stay unknown. Original page receipt times and query completion remain distinct. Fixed diagnostic codes cross the Application boundary; raw server messages do not.

`SnuRequestDispatcher` serializes physical HTTP operations across catalog, every search page and details. Its bounded interactive/watch lanes give waiting watch work a turn after at most two interactive selections. Production pacing has a two-second minimum between physical starts, measured monotonically at actual transport initiation. Source-wide access pauses and cooldowns apply to both lanes. This floor and the monitor profiles are application policies, not evidence that SNU approves a particular request rate.

The production source uses `ISourcePolicyStore` before every physical request. Issued intent, ordered outcomes, access-resume watermarks and replay receipts persist separately from course observations. Access restrictions survive reopen until explicit resume; resume preserves any remaining cooldown. Rate limits and trusted maintenance/service-unavailable responses can extend cooldowns. An unverified HTML maintenance page is not classified by a guessed fingerprint. Known server outcomes are recorded before the dispatcher releases the operation. A failed policy write retains its canonical command, blocks further transport and requires explicit recovery; it never changes a section baseline or delivery acknowledgement.

`SnuCourseGateway` confirms the requested term against catalog metadata. It caches only complete catalog/details reads, with exact query/full-key identity, bounded capacity, original timestamps and monotonic expiry. Seat-count results are never cached as new watch data. Identical metadata operations coalesce; an interactive search may join an existing identical flight. A watch search always starts a new logical flight, so it cannot adopt a response begun before check issuance. Caller cancellation detaches that waiter, and only the last waiter cancels the shared operation. Canceled-but-running work continues to occupy bounded flight capacity until it actually finishes.

## Watch scheduling and observation commits

`WatchQueryPlanner` groups overlapping active watches into catalog-confirmed course queries while preserving separate exact full-term issuance scopes. `WatchMonitorLoop` issues every scope's token before starting the one fresh watch search. `SourceCompletionMapper` maps that response only into its issued scope. The monitor prepares each completion against current store context and retries bounded optimistic conflicts using the same source facts, preserving replay/event identity instead of refetching because a database version changed.

Scheduling uses `TimeProvider` monotonic time with 30/60/120-second target profiles, bounded jitter and at most four logical queries. The physical dispatcher remains serial. Due times derive from logical attempt starts; response latency and overruns do not accumulate missed-run debt. Network/parse failures back off, and longer source cooldowns still win. Manual refresh joins useful work or requests a subsequent fresh operation through the same admission policy. Pause/remove cancels work that no remaining watch needs; a new/resumed generation cannot extend an already-issued check's membership.

Offline/suspended controls stop automatic admission. Recovery replans expiry and staggers overdue work through the same queue. No watches means no automatic catalog polling. Immutable monitor snapshots expose running/waiting/blocked/commit-delayed states and bounded reasons; next-check estimates are not promises of a seat or exact HTTP start.

## Batch delivery and recovery

Watch-management mutations and delivery use the same caller-owned semaphore. Delivery holds it from reading current eligibility through the channel result and its persistence; each SQL transaction finishes before the channel await. Pause may therefore await an already-started send. Once pause/remove completes, an obsolete generation cannot begin another send. Polling does not take this gate and can continue committing checks while the channel waits. The runtime routes mutations through `WatchManagementService` with that exact shared gate; direct store calls cannot substitute for this ordering.

The runtime uses only `BatchDeliveryCoordinator`; the earlier individual-event coordinator remains a tested component and is not run alongside it. A section's batch folds bounded pages through a captured event-ordinal cutoff, then reserves an immutable attempt containing its current recipient union and relational event coverage. One result acknowledges that exact attempt atomically; a later poll cannot invalidate actual channel acceptance. Original events/reasons remain auditable. New post-cutoff events wait for a later fold/attempt, and each newly joined event retains its own retry budget.

`DeliveryStartupRecovery` resolves prior unresolved attempts under database ownership before live senders start. `InterruptedUnknown` is an uncertainty/budget result, never proof of OS rejection or acceptance. `NotSubmitted` consumes no budget. Known channel results whose persistence failed retain their exact canonical command, including its original timestamp, before any new submission for that section. Startup recovery never runs alongside a live coordinator's active attempt.

`BatchDeliveryPump` is the single delivery actor. A separate keyset-paged work reader orders pending sections by oldest event ordinal and full key, so early stale/awaiting-refresh work cannot permanently hide later sections. The pump limits work/folding per turn, advances and wraps pages, prioritizes retained known results, and spaces potential submissions by at least one second after the previous actual submission completes. Retry/fresh-request suppression uses bounded monotonic tracking. Unknown/stale counts request a normal scheduler refresh through a nonblocking owned bridge after the coordinator releases its gate; the delivery worker never awaits a source request.

## Runtime ownership and shutdown

`MonitoringRuntimeSession` owns logical actors, bounded command admission, refresh work, updates and supervision. Startup recovery finishes before monitor/delivery actors start. One shared lifecycle gate orders mutations and submissions. Immutable latest snapshots and sticky commit/failure evidence are retained before bounded UI hints, so UI backpressure cannot block monitoring or lose a delivery wake. Unexpected actor/storage failures stop admission and initiate supervised shutdown. Injected concrete resources remain owned by the caller.

`WindowsMonitoringHost` is that concrete owner. It acquires the SID-scoped global `DatabaseOwnerGate` before opening/migrating the store or constructing the store-backed source/gateway. The dedicated mutex thread acquires and releases on the same thread; its identity has no Windows-session component. Session-local foreground forwarding remains a separate responsibility. The host supplies one store for every persistence capability and one shared lifecycle gate. Its normal profile is fixed; private validation profiles derive only from a marked temporary run GUID and reject arbitrary paths or reparse entries.

Shutdown closes admission, cancels and awaits actual monitor/refresh/delivery work and admitted commands, and retries retained canonical delivery results without resending. Source controls are also owned through completion: canceling a UI waiter does not abandon a queued/running resume or recovery control. The host drains the gateway and any known source-policy write before closing source/store resources, disposes the lifecycle gate, and releases database ownership last.

Cancellation is not proof that underlying HTTP, channel or SQLite work ended. If a known result cannot be saved, the session/host reports `StopBlocked`, retains canonical commands and the required resources/owner, and rejects disposal. Explicit finalization retry retries retained writes and resource closure; it does not restart actors or startup recovery. Private Desktop validation keeps a strong host reference while blocked rather than claiming a clean exit.

No network, SQL or source parsing belongs in a WPF event handler. The student controllers call admitted runtime services and consume immutable projections. The shell's native test adapter remains a feasibility operation, separate from pending course-opening events.

## External boundaries

SNU course data uses a replaceable internal-site adapter. Registration links open in the student's normal browser; planned Genie links use the same boundary. No embedded authenticated session is created. Anonymous transport-session state stays in memory. Never confuse a successful HTTP request with a successfully parsed exact section, or OS notification acceptance with a student seeing a banner.

The Windows shell runs unelevated and owns a stable installed executable path. Registration notification body/button clicks open the fixed official HTTPS URL through Windows directly; they do not start the app or provide it a click receipt. Ordinary application launches route to the existing UI owner. Ordinary shell exit releases live handlers; uninstall removes persistent notification registration before removing the executable. The monitoring host's separate gate excludes another database owner even across sessions. The retained COM callback path is best-effort; its observed failure and protocol redecision are recorded in [ADR 0001](decisions/0001-windows-deployment.md).

The private `--monitor-validation` and `--ui-validation` routes run before native/normal-profile initialization, accept only canonical marked run identities, and reject malformed prefixes without falling through to ordinary startup. Their fake ports exercise the actual host and isolated SQLite state without HTTP or native popups. Normal student startup uses the production source with delivery disabled until M6; private results never establish that live SNU data or real opening popups work. An alert never reserves a seat; registration remains a student action on the official site.
